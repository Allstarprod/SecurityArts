01 Studio · Security architecture

Design review before the incident.

Zero-trust, segmentation and defensible boundaries drawn deliberately, reviewed before the build rather than reconstructed after a breach. We find where the design assumes trust it hasn't earned, and seal a report of the target it should reach.

Request an engagement → All six disciplines

02 Scope

What the engagement covers

  • 01

    Design review

    Architecture and data-flow review against the abuse cases that matter, before code locks the decisions in.

  • 02

    Zero-trust

    Identity-centric boundaries that stop assuming the network is safe. Pragmatic, not dogmatic.

  • 03

    Boundaries and segmentation

    Blast-radius design, so one compromise doesn't become total.

  • 04

    Threat-informed design

    ATT&CK-informed decisions built into the architecture, not bolted on after.

03 Method

How the engagement runs

  1. Scope to an outcome

    We agree the system and the threats that matter: a named goal, not a bundle of hours.

  2. Review the design

    Map trust boundaries and data flows, find where trust is assumed, and propose the target model.

  3. Seal the report

    A signed, dated report: what we reviewed, the target architecture, and what is still open. Sealed, so anyone you share it with can check it hasn't changed.

  4. Re-review

    As the build goes on we review it again. Each re-review gets its own sealed report, so you can show the design was checked, and when.

05 The seal

The report is the deliverable

We seal the report with the studio's SecurityArts account. Anyone you share it with can check that it's the exact file we sealed, and when we sealed it.

What the seal shows

  • Which account sealed the report: the studio's.
  • When it was sealed, as recorded by SecurityArts.
  • That the file hasn't changed since. Change one character and it stops matching.

What it can't show

  • That your systems are secure. It covers the report, not the systems it describes.
  • Anything outside the scope we agreed, or anything found after the seal date.
  • An audit opinion or a certification.
  • A copy that has been edited, re-saved, re-exported or screenshotted. Only the exact file matches.

06 Questions

Questions

Do you review greenfield designs or existing systems?

Both. On greenfield we review the design before code is written; on an existing system we map the real trust boundaries and find where the architecture assumes trust it hasn't earned.

What's the deliverable?

A prioritized set of architectural changes with the reasoning, a target boundary and trust model, and a sealed report of what was reviewed: evidence for your team and your auditors.

How early should we bring you in?

As early as possible. A design review before the build costs far less than re-architecting after an incident. That's the whole point of the discipline.
