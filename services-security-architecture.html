What the engagement covers

Design review

Architecture and data-flow review against the abuse cases that matter — before code locks the decisions in.

Zero-trust

Identity-centric boundaries that stop assuming the network is safe — pragmatic, not dogmatic.

Boundary & segmentation

Blast-radius design so one compromise doesn't become total.

Threat-informed design

ATT&CK-informed decisions baked into the architecture, not bolted on after.

How the engagement runs

  1. Scope to an outcome. Agree the system and the threats that matter — a named goal, not a bundle of hours.
  2. Review the design. Map trust boundaries and data flows, find where trust is assumed, propose the target model.
  3. Seal. A signed, dated record: what was reviewed, the target architecture, and what is still open.
  4. Re-review. As the build progresses we re-issue the seal — proof the design held.

Questions

Do you review greenfield designs or existing systems?

Both. On greenfield we review the design before code is written; on an existing system we map the real trust boundaries and find where the architecture assumes trust it hasn't earned.

What's the deliverable?

A prioritized set of architectural changes with the reasoning, a target boundary/trust model, and a sealed record of what was reviewed — evidence for your team and your auditors.

How early should we bring you in?

As early as possible. A design review before the build is far cheaper than re-architecting after an incident — that's the whole point of the discipline.
